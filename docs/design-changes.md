# 設計書 v0.1 からの変更点

元の設計書(v0.1)との差分を記録する。設計書本体(`docs/design.md`)はこのリポジトリに未収録。

## 2026-10-31

### 日常会話の既定をローカルLLM(Llama)にする
- 変更前(v0.1 §1.2, §6.2): 日常会話は OpenAI API。
- 変更後: **日常会話の既定はローカルLLM**。OpenAI API はオプションのオンライン接続先として残す。
- 実装: `LocalLLMAdapter`(agentType `local`)。Ollama / llama.cpp server / LM Studio など OpenAI 互換の `/v1/chat/completions` を持つ実行基盤を対象にする。履歴の正本は Gateway(SQLite)。`ConversationAdapter` 基底クラスに履歴・中断・永続化を集約し、通信方式だけを派生クラスが持つ。
- 効果: 発話が外部に出ない(§9.3)、API 利用枠に依存しない(Codex と違い上限で止まらない)。

#### 決定事項 (同日)
1. **最新情報の質問は、Gateway に検索 API を足して扱う。** Gateway が発話から検索の要否を判定し(ルールベース、話題語: 天気・ニュース・為替など / 「検索して」)、検索結果を「そのターンだけの文脈」としてモデルに渡す。結果に無いことは推測させず、検索失敗・結果なしのときは「確認できなかった」と伝えさせる(§5.6)。履歴には文脈を保存しない。
   - ツール呼び出し(モデルが自分で検索を選ぶ方式)は採らない。14B クラスでは判断が不安定になりやすく、遅延も増える。必要になれば後で再検討。
   - プロバイダは差し替え式。実装: Brave Search API、SearXNG。どちらも**実環境では未確認**。
   - **プライバシー:** 検索が走ると、発話の全文が検索プロバイダ(外部)に送られる。`onSearch` で送信先と内容を通知できる。設定画面で利用者が確認できるようにする(§9.3)。
   - 場所の指定がない「今日の天気」は、検索クエリに地域が無く精度が出ない。既定の地域設定は未実装。
2. **ルーターの宛先名は `chat`**(日常会話の論理名)。バックエンド(ローカル/OpenAI)は設定で替える。「ChatGPT/OpenAI」の明示指定は、いったん `chat` に解決する。評価結果は変更前後で同一。
3. **モデルは `qwen3:14b`(Ollama)。** 推論モデルのため:
   - 本文の `<think>…</think>` はタグが途中で分断されても除去する(読み上げ・保存の両方から除外)。別フィールドの reasoning は読まない。思考の停止は下記の実測を参照(`/no_think` 単独では止まらず、`reasoning_effort:"none"` で止まる)。
   - Ollama の `/v1` は1リクエスト単位で文脈長(`num_ctx`)を指定できない可能性がある。既定の文脈長が短いと履歴が黙って切られる。`npm run smoke:local` の合言葉テストで確認し、必要ならサーバー側の既定文脈長を上げる。

#### 残る検討事項
- ルーターのローカルLLM(Phase 0B 方式C/D)も同じ実行基盤を使える。Embedding も同じ基盤で試せるかを確認する。
- 検索の既定地域、検索結果の出典を読み上げでどう伝えるか。

## 実機確認: ローカルLLM (qwen3:14b / Ollama / SearXNG, Windows) 2026-10-31

`npm run smoke:local` の結果:

| 項目 | 結果 | 所見 |
|---|---|---|
| 日本語の短い応答 | 動作 | 思考タグの混入なし。**初回トークンまで 12.1 秒**(音声用途には遅い)。出力トークン 276 に対し見える本文は約50文字で、思考が行われている可能性。モデル読み込み(コールドスタート)を含む可能性もあり、未切り分け |
| 合言葉テスト(履歴約6000文字) | **失敗** | 入力トークンが 4079 で頭打ち = Ollama の既定の文脈長 4096 で履歴が**黙って切られている**。最初の発話が失われた |
| 検索 → 回答 (SearXNG) | 動作 | 出典付きで回答。ただし全体 21.5 秒、回答は「関東以西」と広く、東京に絞れていない。内容の正確さは未確認 |

対応:
- **文脈長の警告:** `contextTokens` を設定すると、入力が 90% に達したとき `warning(context_nearly_full)` を出す。黙って切られる状態を検知できるようにした。
- **サーバー側の設定が必要:** Ollama の文脈長を上げる(環境変数 `OLLAMA_CONTEXT_LENGTH`、または Modelfile の `num_ctx`)。Ollama の `/v1` はリクエスト単位で文脈長を指定できないため、Gateway 側では直せない。
- **遅延の切り分け:** `npm run diagnose:thinking` で、思考の量・到着時間を条件別(/no_think、reasoning_effort:none、指定なし)に測る。
- **ウォームアップ:** smoke に追加。モデルの常駐(`OLLAMA_KEEP_ALIVE`)を伸ばさないと、アイドル後の最初の発話で毎回読み込みが発生する。
- 未検証の仮定: `reasoning_effort: "none"` が Ollama の `/v1` で思考を止めるか。

### GPU の占有方針 (2026-10-31)
要望: GPU は実験に空けておきたい。モデルを常時ロードしない。
- **常駐させない。** `OLLAMA_KEEP_ALIVE` は長くしない(既定の5分、または短く)。アイドルが続けば自動で解放される。
- **使うときだけ先読みする。** `AgentAdapter.prepare()`(任意)を追加。Android の PTT 開始時に呼ぶと、発話・音声認識の間にモデルの読み込みが済む。`LocalLLMAdapter` は `OllamaLifecycle.warm()` で先読みする(Ollama のネイティブAPI。`/v1` は keep_alive を受け付けない)。先読みの失敗は無視し、実際の要求時に再試行される。
- **実験前に解放できる。** `npm run llm -- unload`(または `ollama stop <model>`)。`npm run llm -- status` で読み込み状態と VRAM、GPU 割合を確認できる。
- **GPU が実験で埋まっているとき:** 一部が CPU に載る(GPU 割合が 100% 未満)と遅くなる。`status` が割合を表示して知らせる。
- 未検証: `/api/generate` の空リクエストによる読み込み、`/api/ps` の項目名は Ollama の仕様の記憶に基づく。実機で `npm run llm -- warm` を確認する。
- 未解決: 読み込み時間の実測(初回トークン 12 秒のうち読み込みが何秒か)。VRAM の節約には、文脈長を必要以上に大きくしない(16384 で KV キャッシュが約2.5GB増える概算)こと、小さいモデルへの切り替えも選択肢。

### ローカルLLMの読み込み時間 (実測, 2026-10-31)
`npm run llm -- status|warm|unload` を Windows で実行: 3操作とも期待どおり動作(Ollama の `/api/generate` による読み込み・解放、`/api/ps` による状態取得を確認)。`keep_alive:"5m"` を指定した読み込みの解放予定は約5分後で、指定が効いている。qwen3:14b は VRAM 9.3GB、GPU 100%。

**コールドスタートの読み込みは 41.2 秒**(9.3GB を約 230MB/s)。ディスク読み込み速度に近く、OS のファイルキャッシュが効いていれば短くなる可能性がある(未測定)。PTT 時の先読みで隠せるのは発話〜音声認識の数秒だけで、完全なコールドスタートは隠せない。

対応:
- `status` イベント(`model_loading`): 読み込み中と分かったら送信前に通知する。Android は音声で「モデルを起動しています」と伝え、無言で待たせない(原則8)。
- `OllamaLifecycle.touch()`: ターン終了ごとに、Gateway 設定の `keepAlive` で解放時刻を更新する。Ollama の環境変数の既定値に依存せず、「会話の合間は残し、しばらく使わなければ解放」を Gateway で調整できる。
- 判断材料: 実験の合間にどれくらいで GPU を空けてよいか(keepAlive の値)。モデルの置き場所(SSD か)。小さいモデル(qwen3:8b 等)への切り替えで読み込み時間・VRAM・応答速度がどう変わるか。

### 思考の遅延の実測 (`npm run diagnose:thinking`, qwen3:14b, 2026-10-31)
実験で GPU を使用中のため所要時間は参考値。トークン数は競合の影響を受けない。

| 条件 | 別フィールドの思考 | 生成トークン | 見える本文 |
|---|---|---|---|
| A `/no_think` のみ(旧既定) | 1675文字 | 446 | 26文字 |
| B `/no_think` + `reasoning_effort:"none"` | 0文字 | 10 | 17文字 |
| C 指定なし | 516文字 | 153 | 33文字 |

- **`/no_think` は Ollama の `/v1` では思考を止めなかった。** `reasoning_effort:"none"` が効く。初回トークン 12 秒の主因は、見えない思考の生成だったと考えられる(smoke の初回トークンは見える本文までを測る)。
- 既定で `reasoning_effort:"none"` を送る(`suppressThinking:false` で無効化、`extraBody` で上書き可)。思考を持たないモデルでは拒否される可能性があり、未確認。
- GPU を実験と共有すると、読み込み 29 秒・生成が遅くなる。実験中の対話応答は遅くなり、実験側にも負荷をかける。

## WebSocket 層 (2026-10-31)

実装: `server.ts`(Connection Manager)、`gateway.ts`(司令塔)、`protocol.ts`、`speech.ts`(Speech Formatter)、`catalog.ts`。仕様は `docs/protocol.md`。
偽 Adapter・偽 app-server・偽 fetch でテスト(Gateway 18 + サーバー 8 + 読み上げ 6 件)。Ollama なしで起動し WebSocket から接続して、`ローカルLLMに接続できません` が再試行可能な拒否として返ることを確認した。**実際の Android 端末、Ollama、Codex を通した確認はまだ。**

設計判断:
- **認証:** 接続時の `Authorization: Bearer`(デバイスごとのトークン、24文字以上)。常時比較(全デバイスと比較)で時間差を出さない。待ち受けは既定 127.0.0.1。`0.0.0.0` は明示しない限り拒否(§9.1)。TLS はなし(Tailscale の暗号化を前提)。
- **重複排除と結果不明 (§8.4):** `requestId` ごとに状態を SQLite に記録(`received → dispatching → accepted/failed`)。重複は前回の結果を返すだけで再実行しない。外部 Agent に触れる直前に `dispatching` を書き、起動時に実行中のまま残っていた要求は `indeterminate` にする。**Gateway だけでは外部 Agent への Exactly-Once は保証できない**ので、自動再実行はしない。
- **イベントの再送:** 読み上げ要求は保存してから送る。`ack` または `hello.lastEventId` で削除。保持 24 時間。一時的な通知(モデル起動中)は保存しない。
- **読み上げ:** チャットは文単位でストリーミング(体感遅延を減らす)。Codex は途中の発言(`phase≠final_answer`)を読まず、最終回答だけを `high` で読む。1ターンの上限 600 文字(全文は履歴に残る)。コードブロックは読まない。
- **エラー:** Adapter のエラー種別を、読み上げ可能な日本語と retryable に変換。ターンの失敗は `critical`。Codex の承認要求は承認せず「パソコンで確認してください」。
- **ルーターの入力:** 各 Adapter のセッション一覧(30秒キャッシュ。1つの Agent の失敗で他を止めない)。キーワードはタイトルから文字種で抽出する暫定実装 → `session_summaries` による置き換えが必要。ルーターは評価用パッケージからの暫定 import(A2 相当の設定)。
- **記録:** `routing_decisions` に発話とルーティング判定を保存する(誤配送率の実測用)。**発話本文が残る**ので、保存期間と削除方法の設定が未実装(§9.3 の宿題)。

未実装・未決:
- 音声による確認の回答(「2番」「キャンセル」)の解釈。現状は端末が添字を送る。
- 認証トークンの発行・失効の手順(現状は環境変数)。レート制限なし。
- Android 側の実装。`routing_decisions` の保存期間設定。`session_summaries`。Codex の割り込み。

## Android クライアント (2026-10-31)

実装: `android/core`(ビルド・テスト済み)と `android/app`(未ビルド)。詳細は `docs/android.md`。

- **この開発環境では Android SDK を取得できなかった**ため、アプリ本体は一度もコンパイルしていない。確認できたのは、`core` の単体テストと、本物の Gateway(モック)に Kotlin のクライアントでつないだ結合テストまで。
- **結合テストで見つけた設計上の穴を修正した:** 端末が覚える ack の位置は、Gateway の DB ごとに意味が違う。DB を作り直す・別の Gateway につなぎ替えると番号が 1 から振り直され、端末は新しいイベントを「読み上げ済み」として黙って捨て、Gateway は端末の申告で別の DB の未配信イベントを削除しうる。対策として、Gateway に永続的な識別子(`instanceId`)を持たせ、`hello.ok` で通知し、端末が `hello` に載せる。違うときは、端末は位置を捨て、Gateway は位置を無視して全件を再送する。修正を外すと回帰テストが失敗することを確認済み。
- **設定の永続化:** Gateway は `.env` から設定を読む(`npm run gateway:init` でトークンを自動生成して作成。実際の環境変数が優先。`.env` はコミットされない)。
- **Android 開発用のモック Gateway:** `npm run gateway:mock`。Ollama・Codex なしで、本物のルーター・重複排除・再送を通して、台本どおりの応答を返す。
- 未決: 確認要求への音声回答は、いまは次の PTT で受ける(自動で聞き始めない=マイクは PTT のときだけ、という方針による)。走行中の運用として妥当かは実機で評価する。

### 会話モデルを GPU に載せない (2026-10-31)
**背景:** 会話モデル(qwen3:14b)が VRAM を占有し、同じ GPU を使う他の実験がメモリ不足で止まった。実験を優先する。
**決定:** 会話モデルは CPU とメモリだけで動かす。モデルは `qwen3:4b` に下げる(メモリは目安で 2.5GB 前後。実際の値は `ollama ps` で確認)。

構成:
- **CPU 専用の Ollama を別ポート(11435)で起動する:** `npm run ollama:cpu`。`CUDA_VISIBLE_DEVICES=-1`(AMD は `ROCR_VISIBLE_DEVICES` / `HIP_VISIBLE_DEVICES` も)で GPU を見えなくする(Ollama の公式の手順)。待ち受けは `127.0.0.1` のみ、並列数とロード数は 1。普段使いの Ollama(GPU)には影響しない。モデルのファイルは共有される。
- **優先度を下げて起動する**(`VAG_CPU_PRIORITY=normal` で無効)。実験の CPU を奪わない代わりに、実験が CPU を使い切っていると応答が遅くなる。
- **Gateway の `.env`:** `OLLAMA_BASE_URL=http://127.0.0.1:11435/v1`、`LOCAL_MODEL=qwen3:4b`、`LOCAL_DEVICE=cpu`、`LOCAL_HISTORY_CHARS=3000`(CPU は長い履歴の処理が遅い)、`LOCAL_MAX_TOKENS=300`(返答を短く打ち切る)。`npm run gateway:init` が新規の `.env` にこの構成を書く。
- **確認:** `npm run llm -- warm`。`LOCAL_DEVICE=cpu` のとき、「CPU のみで動いています(想定どおり)」なら成功。GPU を使っていれば「要確認」と、直し方が出る。

**未検証(実機の CPU での測定が必要):** 生成速度とレイテンシ。`npm run smoke:local` が「速度の目安(トークン/秒)」を出す。音声には 5 トークン/秒以上が欲しい。足りなければ `qwen3:1.7b` など更に小さいモデルへ、余裕があれば `qwen3:8b` へ。日本語の応答の質は、サイズを下げると落ちる。
**注意:** 検索結果を使う質問は、毎回システム指示が変わるため、前の会話の計算結果が再利用されにくく、CPU では遅くなる。

#### 実機で分かったこと: GPU を隠す設定だけでは足りなかった (2026-10-31)
`npm run llm -- warm` で、CPU 専用のつもりの Ollama(11435)が `qwen3:4b` を **VRAM 4.8GB・100% GPU** で読み込んだ。設定の読み込み自体は正しかった(`LOCAL_MODEL`・`LOCAL_DEVICE` が反映され、判定が働いた)。原因は未特定: (a) `CUDA_VISIBLE_DEVICES=-1` が効いていない、(b) 11435 で答えているのが `ollama:cpu` で起動したものではない、のどちらか。
- **起動ログの見張り:** `npm run ollama:cpu` は Ollama の起動ログを中継し、GPU を検出したら警告する(CPU のみなら確認を表示)。(a) と (b) の区別に使う。
- **派生モデル(環境変数に頼らない方法):** `npm run ollama:model` が `PARAMETER num_gpu 0`(GPU に載せる層を 0 に)と `num_ctx 4096` の派生モデル(例 `qwen3-4b-cpu`)を作る。どの Ollama で動かしても CPU 実行を指定できる。**この指定で VRAM が 0 になるかは、実機で未確認**(`npm run llm -- warm` の判定と、`ollama ps` の PROCESSOR 列で確認する)。
- 4B のモデルで 4.8GB は、重み(約 2.5GB)に加えて、既定の文脈長で確保される KV キャッシュが大きいため、と推測される。派生モデルは `num_ctx` も固定する。

#### 確認済み (2026-10-31, Windows 実機)
`npm run ollama:model` で作った派生モデル `qwen3-4b-cpu`(`num_gpu 0`)を `npm run llm -- warm` で読み込むと、**「CPU のみで動いています。モデル全体 3.0GB、VRAM 0」**と判定された。環境変数で GPU を隠す方法(`ollama:cpu`)は、この環境では GPU を検出したまま(無効化が効かなかった)だったが、**モデル側の指定で目的は達成できた。**
- 未確認: 読み込み中に、プロセスが GPU 側へ少量のメモリ(CUDA のコンテキスト等)を確保していないか。タスクマネージャーの「専用 GPU メモリ」で、モデルの読み込み前後を比べて確認する。
- 未測定: CPU での生成速度と初回トークンまでの時間(`npm run smoke:local`)。
- `ollama:cpu` の別インスタンスは必須ではない。普段使いの Ollama(11434)に派生モデルを作って `OLLAMA_BASE_URL` をそのポートにしても、同じ指定が効くはず(未検証)。

#### CPU での初回測定と、見つかった異常 (2026-10-31, `npm run smoke:local`, qwen3-4b-cpu)
結果: ウォームアップ 374 秒、「一言で自己紹介して」に **2492 トークン・615 秒**、初回トークン 567ms、速度 4.1 トークン/秒。
- **異常:** 短い質問に 2492 トークン・10 分は異常。初回トークンが 567ms と速いのに 10 分続く、という組み合わせは、**開始タグのない思考の文章**が「見える回答」として流れていると考えると説明がつく(Qwen3 は思考ブロックの開始をプロンプト側で行うため、出力は「考え → `</think>` → 答え」になる)。従来の `<think>` 除去は開始タグを前提としており、通してしまう。音声なら思考を読み上げることになる。
- **推測される原因(未確認):** 派生モデルでは、Ollama の思考の分離(`reasoning_effort: "none"` や別欄への出力)が効いていない。14B(元のモデル)では効いていた。確認方法: `ollama show qwen3:4b` と `ollama show qwen3-4b-cpu` の Capabilities の比較。
- **対策(実装済み):** (1) 開始タグのない `</think>` も除去する(/no_think で空の思考ブロックが出る場合に読み上げへ混ざらない)。(2) 返答に既定の上限(`max_tokens` 400)を設け、暴走で数分続かないようにする。(3) `smoke:local` が `LOCAL_MAX_TOKENS` を使うようにし、実運用と同じ条件で測る。
- **限界:** 開始タグのないまま長い思考文が出る場合は、取り除けない(閉じタグが来るまで思考か判断できず、保留すると音声の遅延が大きいため)。**根本対策は、思考を出さないモデルを使うこと**(Qwen3 の非思考版 `instruct` 系など。タグ名は Ollama のライブラリで確認する)。
- 速度 4.1 トークン/秒は、思考の文章を生成しながら、実験と CPU を共有した条件での値。非思考のモデルで測り直す。

#### 訂正と整理 (2026-11-01)
- **訂正:** 思考の文章が流れた原因として、「派生モデルでは Ollama の思考の分離が失われた」と推測したが、`ollama show` の Capabilities を元のモデルと比べて**差がなかった**。この推測は否定された。原因は未特定のまま(次の確認: `smoke:local` の `回答:` の行、非思考版モデルでの測り直し)。除去処理の強化と上限の設定は、原因によらず有効なので残す。
